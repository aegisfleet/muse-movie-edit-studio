# 設計メモ (docs/DESIGN.md)

本リポジトリの設計判断と、処理時間の目安をまとめる。個別の検証経緯は残さず、結論とパターン別の数値だけを管理する。

## 成果物仕様

- `outputs/final.mp4`: 1080×1920 (9:16)、30fps、合計尺は YAML の `project.duration_sec`（標準 30.0 秒 = 900 フレーム）、H.264 / AAC 48kHz

## 決定事項

### 1. 設定 YAML を唯一の真実とする

- Remotion コンポーネント内に動画固有のテキストを直書きしない。`run_pipeline.py` が YAML から `public/project_config.json`（開始・終了フレーム計算済み）を生成し、コンポーネントはそれをループ描画する
- 理由: エージェントが編集するのは YAML だけで済み、TypeScript の改変ミスによる合成破綻が起きない

### 2. エンコーダは実行環境で自動選択する

- `scripts/run_pipeline.py` の `select_video_encoder()` が、NVIDIA GPU デバイスの実在を確認して NVENC / libx264 を切り替える。環境変数 `VIDEO_ENCODER=nvenc|x264|auto` で上書き可能
- 理由: ffmpeg のエンコーダ一覧に `h264_nvenc` が載っていても、GPU が無い環境（Muse VM、CI、一般的なクラウド VM）では実行時エラーになる

### 3. ナレーションは Muse の Meta AI TTS を第一候補とする

- `scripts/generate_narration.py` がバックエンドを自動選択する。Muse 環境（`/opt/hatch/bin/tts` が存在）では Meta AI ボイスで合成し、それ以外では edge-tts（日本語ボイス）を使う。声は `--voice` で指定する
- 理由: ローカル TTS モデルはモデル本体と参照音声の別途管理が必要で、軽量な VM では実行も重い。固定ボイス ID を使うことで「シーンごとに別人の声になる」問題を避ける
- 尺ガードレール（無音トリム + `atempo` 圧縮 + 末尾フェード）で、ナレーションがシーン尺を超えないことを保証する
- Meta AI ボイス (avocado_v2) で有効なのは MAI_01（高めの声）と MAI_03（既定）の2種のみ。他の ID を指定しても MAI_03 にフォールバックする

### 4. 音楽 (BGM) は生成 AI に寄せない

- BGM は実音サンプラー + DSP の `generate_sampler_bgm.py` / `generate_dynamic_bgm.py`、または素材持ち込みとする
- 理由: 音楽のみを単独生成する経路はなく、DSP 生成は再現性があり音響品質の設計もコードとして管理できる

### 5. 検証はローカル CV を主判定とし、目視を補助に使う

- Gate 1（レンダリング前）と Gate 2（最終成果物）で `verify_composition.py` が被写体の中央オフセット、サイズ占有率、鮮鋭度を判定する（LLM トークン消費なし）
- 数値スコアだけでは意味の判断（表情、被写体の向き等）ができないため、エージェントの目視で候補フレームを確認し、必要ならシーンを差し替える併用が標準

### 6. 素材と生成物は Git 管理しない

- `inputs/`、`public/audio/`、`outputs/`、モデル重み（`*.pt`）は `.gitignore` で除外する。リポジトリはコードと設定（YAML / JSON）のみを管理する
- 素材の受け渡しはチャット添付、写真ライブラリ、接続デバイス、外部ストレージ経由で行い、`inputs/` に配置する
- チャット添付には上限がある（web版: 動画 約100MB、その他 約25MB）。100MB を超える素材は Google Drive 等の外部ストレージ経由とする。GB 級の GoPro 原画はこの経路が前提になる

### 7. プロキシは任意オプション（標準手順には含めない）

- `analyze_subject.py --proxy` で低解像度プロキシ（幅854px、`scratch/proxy/` にキャッシュ）を解析でき、結果（正規化座標・タイムスタンプ）は原画にそのまま適用できる
- ただしプロキシ生成は初回のみ約10.5分（4K 260秒素材）かかり、損益分岐は同一素材で 解析 約4回 / レンダリング 約3回 以上の反復が必要。通常の制作では原画を直接扱う方が速いため、標準手順には含めない
- 品質スコアの絶対値は解像度で変わるため、原画解析とプロキシ解析のスコアを方式間で比較しない

### 8. 色変換とグレーディングは最終出力でのみ有効化する

- HLG / PQ の HDR 入力に対するトーンマップと、シーンのグレーディング（カーブ）は、どちらも 4K フル解像度のまま処理されるため高コスト（下表参照）
- 構成・カットの確認用レンダーでは両方を省略してよい（色は最終と異なるが、構図とタイミングの確認には足りる）。最終出力では必ず両方を有効化する

## 処理時間の目安（パターン別）

基準環境: Muse VM（Ubuntu 24.04、2 vCPU、RAM 7.7GB、GPU なし、ffmpeg 8.1.2、Node 24）。基準素材: 4K HLG 260秒・30秒ショート（5シーン×6秒）を制作した場合の実測。素材やシーン数で比例的に変わる。

### 前処理・解析

| 処理 | 時間 | 備考 |
|---|---:|---|
| 被写体解析（原画、間隔3秒、87サンプル） | 約3分42秒 | 間隔が処理時間を決める。処理が素材の実時間を超えるなら間隔を広げる |
| 被写体解析（プロキシ、生成後） | 約30秒 | 生成は初回のみ約10.5分 |
| Gate 1 / Gate 2（verify_composition） | 各 約30秒 | シーン中心フレームのみを評価 |
| ナレーション生成（5シーン、Meta AI TTS） | 約10秒 | |
| BGM 生成（30秒、numpy 合成） | 約3秒 | |

### レンダリング（Step 1 = ffmpeg、Step 2 = Remotion 900フレーム）

| パターン | 解像度 | トーンマップ | グレーディング | Step 1 | Step 2 | 合計 | サイズ |
|---|---|---|---|---:|---:|---:|---:|
| 本番（最終納品） | 1080×1920 | ○ | ○ | 424秒 | 約466秒 | 約890秒（約15分） | 73.8MB |
| SD | 540×960 | ○ | ○ | 342秒 | 170秒 | 512秒 | 29.3MB |
| 確認用 540 | 540×960 | × | ○ | 203秒 | 170秒 | 約373秒 | ― |
| 確認用 270 | 270×480 | × | ○ | 166秒 | 122秒 | 約287秒 | 8.2MB |
| 最速 270 | 270×480 | × | × | 124秒 | 122秒 | 約245秒（約4分） | ― |

読み方の要点:

- Step 1 の律速は入力の 4K デコードと、4K のまま処理される色変換（トーンマップ / グレーディング）。出力解像度を下げる効果は Step 1 では小さく、Step 2 で大きい
- 解像度を 540 以下に落としても Step 1 は頭打ちになる（270 で 166秒、360 で 191秒）。確認用途の実用下限は 270×480（被写体と構図は判読可、テロップの文字確認は 540 が目安）
- Step 2 の並列度は `concurrency=1` が最速（2 にすると 270 でも 122秒 → 162秒と遅くなり、メモリ不足で落ちるリスクも上がる）。Step 2 の所要時間はメモリ空きで揺れる（HD で 466 から 574秒）
- Step 1 への入力をプロキシに変えると 424秒 → 163秒になるが、プロキシ生成（約10.5分）が先行するため通常制作では使わない（決定事項 7）
- 推奨フロー: Gate 1（約30秒）で構図を固める → 必要なら最速 270 / 確認用 540 で流れを確認 → 本番 HD で最終出力

## 環境メモ

- 日本語フォント: Noto CJK が必要
- Remotion のレンダリングには Headless Chrome が必要（環境に無い場合は Remotion が初回に自動取得する）
- SDR 入力を HLG 用 zscale チェーンに通すと失敗するため、色変換チェーンは入力の転送特性で分岐している（`run_pipeline.py` が自動判定）
